# Project architecture
- Admin financial totals use verified payment fields, rider goods expenses and separate charges; completed refund amounts are reconstructed from chronological financial audit balances at completion, never the mutable current balance, and unknown historical amounts are disclosed rather than guessed.

- Shared Table paginates rendered data rows after consumer filtering/sorting, resets on row identity changes, and keeps pagination outside horizontal scrolling; consumers must pass complete datasets (not presentation slices) so reports and exports retain all records.

- Password login resolves mobile and email profile contacts only inside phone-login, including legacy phone-alias accounts; keep privileged lookup and publishable password-validation clients separate and never expose emails before authentication. New registrations prefer real Auth email when supplied and retain synthetic aliases for phone-only accounts; no-session signup requires email confirmation.

- Customer home queries only the signed-in customer's orders and separates active from closed history; public and staff home experiences stay unchanged.
- Shared Button reports click feedback, Promise-aware loading and explicit loading states to the singleton ScreenLoader via reference-counted tokens; keep labels visible and do not infer pending work from disabled permissions, so concurrent actions share one screen overlay without premature dismissal.
- Customer-declared payment amounts and proof history are saved atomically through submit_customer_payment; summaries may include pending declarations, but operational gates always use manager-verified funds.

- Reconciled order readiness uses payment_verification and paid_amount_pkr against the order total; payment_status is a legacy fallback only, so stale upload flags cannot block verified orders.
- Keep the initial payable snapshot backward-compatible (goods plus bundle); display Order Total as snapshot minus bundle. Settlement RPCs and triggers compare verified payment with goods shopping expense plus bundle and third-party delivery charges once; reconciled orders use one payment-proof flow, while legacy orders retain separate delivery payments.

- Keep iOS app icons in the native AppIcon asset catalog and Android icons in density-specific launcher resources, derived from the approved app icon; native launchers require platform-specific sizes and adaptive foreground safe areas.
- Set Android minimum SDK in android/variables.gradle and inherit it in app/build.gradle; the release regression test protects Play automatic-protection compatibility without editing generated Capacitor files.
- Keep legal and data-deletion information on public pages linked from the shared footer so customers can access them without signing in; deletion requests use the support contact unless an actual deletion workflow is implemented.
- Admin user viewing, editing and deletion go through the manage-users function with server-verified admin authorization; saves use a service-role-only transactional RPC and deletion is blocked for self or linked operational history to prevent accidental loss of orders.
- Admin account creation replaces the signup default through a service-role-only transactional role RPC after server-side admin authorization; direct signup relies on the existing customer trigger, never client-side role inserts.
- Admin role edits use manage-users and the transactional role replacement RPC; never delete and insert roles from the browser, so role changes cannot leave users without access.
- Payment screens read active bank_accounts through shared BankAccountDetails; admin-only RLS protects mutations and placeholder bank numbers must never be used as a fallback.
- Store order attachments as private bucket-relative paths; use StorageImage/openAttachment to refresh signed access, including compatibility with old public URLs, rather than saving expiring links.
- Capacitor sync runs the native photo-permission hook on Mac to set iOS usage descriptions; regenerate plugin registration with cap sync instead of hand-editing generated Gradle files.- Order financials (paid amount, shopping expense, balance, refunds) change only through the SECURITY DEFINER RPCs verify_order_payment, submit_shopping_expense, verify_shopping_expense, reopen_shopping_expense and update_refund_status; never update those columns directly from the client, so verification rules and the order_financial_events audit trail cannot be bypassed.
- Item prices, rider item purchases (multi-photo proofs, not-available items at Rs. 0) and delivery release go through review_order_item, submit_item_pickup and mark_ready_for_delivery RPCs; order_total_pkr and shopping_expense_pkr are derived server-side from item rows, and a trigger blocks In Delivery/Delivered until ready_for_delivery_at is set, except verified bills with a refund owed to the customer, so totals and delivery gates cannot be bypassed from the client.
